# 真实提示、回答及自纠案例

这些摘录来自本次可见聊天和实际工具输出。引号内为原话；其他文字是整理说明，不冒充模型逐字回答，不包含私有推理。功能验收仍由原始运行回执和用户观察决定。

## 案例一：按当前成果与竞赛要求整理

用户提示：“帮我把main分支的内容给我拉取到[usrp-zedboard-mimo-hdmi]这个仓库，作为一个完整的成果，我要用来参加比赛，一些冗余部分就不需要了”。链接指向目标仓库。

用户补充：“请你按照这个文件的要求来进行组织，我的赛道是自主选题赛道初级组”。

模型可见回答摘录：“目录已按初级组指南整理为源码、仿真验证、构建、上板、数据、技能和报告七部分。”

用户纠正交付口径：“不要给我待完成的，我目前这版就作为是完整的工程”。

模型回答摘录：“明白，就把当前已验收版本作为完整工程交付，不再把后续优化列为本版待办。”

落实：冻结源 main 提交，分离当前功能代码、必要运行依赖和代表性证据，不导入未完成分支。以完整的有限收完再播成果交付；按实测帧率报告，不扩大为持续实时功能。交付目录、源哈希与指南对照见 ../requirements.md、../release.md 和 ../../build/source_manifest.json。

## 案例二：精简运行包时遗漏 Python 运行依赖

触发：为删除开发缓存而从分发树省略 .pyc，ARM 离线解码报 `ModuleNotFoundError: No module named 'encodings'`。本根树部分标准库只有字节码，并非可重生成的源码缓存。

纠正：从已冻结的原运行树找回 1025 个必需标准库文件，重打包、全流校验，再在新恢复目录执行真实 ARM NULL 解码。结果为 25 个 AU 通过，未声明 RF 或物理 HDMI 测试。见 ../../sim/verification/migration_arm_decode.json。

提炼：清理依赖必须通过实际入口验证。不能按扩展名批量删除 pyc，更不能把“文件都在”当“能运行”。

## 案例三：精简源码后恢复 Vivado 构建入口

触发：从精选源码恢复新目录运行 Vivado validate，发现配方无条件 add_files 引用了 rf_static_clkdiv.v，初版精选清单缺此文件。它虽未作为最终综合静态输入使用，仍属于当前构建入口依赖。

纠正：从冻结 main 工程包找回原文件，按历史 SHA 核对，加入源码恢复清单；同时补齐 ADI IP 配置所需的 8 个 gtcl/ttcl/配置文件，保持 RTL 字节不改，再运行新工程/BD 校验。797 个源码/配置文件的新目录构建入口已通过。该过程与历史源身份审计相互独立，不通过修改算法解决打包问题。

提炼：源码闭包包含配方读取依赖、生成器和最终综合输入，不能只打包最终综合报告里出现的文件。最终结果见 ../../sim/verification/migration_fpga_validation.json。
