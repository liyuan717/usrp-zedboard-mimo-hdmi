# MRF1-v1：USRP 发送端完整工程交付要求

## 1. 目的与边界

本文是 `rf-air-interface-v1` 协议分支中 USRP 发送端的**强制交付与验收约束**。实现者必须以本目录的空口规范和确定性测试向量为准；若本文与其冲突，PHY 比特级格式以空口规范和测试向量为准，本文规定的是工程完整性、吞吐、运行安全和验收证据。

目标是把源数据（第一阶段为任意 128 B 二进制载荷，第二阶段为 RVF2/H.264 片段）持续、可观测地送入两路 USRP TX 并通过 MRF1-v1 空口发送，使 ZedBoard 接收端能够按协议恢复。它不是 Wi-Fi、LTE 或 OFDM 工程；不得混用这些协议的帧格式、导频、同步或速率假设。`MHGD` 是接收端的 MIMO 检测算法，不是发送端编码、神经网络模型或视频压缩器。板端 `RXTH` 是本地 DMA 元数据，**不是**空口字段，USRP 不得发送或依赖它。

本阶段的先后关系必须明确：先完成「USRP -> 128 B/stream MRF1 功能闭环」，再接入 RVF2 和视频性能闭环。低速、短时、反复播放的功能演示不能宣称完成视频目标。

## 2. 已冻结的 PHY 与容量边界

USRP 工程必须固定并在启动日志中逐项打印以下配置，不得通过隐式默认值漂移：

- MRF1-v1，复采样率 4 MSPS，符号率 1 Msymbol/s；双发射流、QPSK、每符号 4 倍采样。
- 根升余弦成形：roll-off `beta=0.35`，41 taps。每个 RF 帧为 950 个符号，加 40 个滤波尾部采样，恰为 `950 * 4 + 40 = 3840` 个复样点。
- 每个 RF 帧内两路空间流同时存在；每流一个包，包格式为 20 B header、128 B payload、4 B payload CRC，即每流 152 B。20 B header 中的 header-CRC 归属以规范为准。
- 每包 608 个 QPSK 符号；header 占 80 符号，header 后的 `128 B payload + 4 B payload CRC` 占 528 符号。帧符号布局为：leading guard 32、preamble 96、separator 12、training-1 64、separator 12、training-2 64、separator 12、header 80、payload/CRC 528、9 组双导频 18、trailing guard 32，总计 950。

一个 RF 帧时长为 `3840 / 4,000,000 = 0.96 ms`，理论上限为 1041.667 RF 帧/s。两流合计裸 MRF payload 为 256 B/RF 帧，即 **2.133333 Mb/s**；这是无空闲、无重传、无额外业务开销时的上限，不能作为稳定业务吞吐承诺。

RVF2 模式中，每流 128 B MRF payload 最多承载 100 B fragment data（其余为 RVF2 头）。因此两流合计最大有效片段数据为 200 B/RF 帧，即 **1.666667 Mb/s**，且尚未扣除访问单元头、奇数片冗余填充、控制帧、队列裕量和空口失效。若采用奇数片在另一流的幂等复制，必须计入实际吞吐损失，不能按 200 B/RF 帧虚报。

`1024 x 600` 的 RGB565 原始视频在 30 fps/60 fps 分别为 294.912/589.824 Mb/s，必需使用压缩。现有 H.264 参考样例（1024x600、30 fps、30 帧、173491 B）为约 1.388 Mb/s，已占 RVF2 理论上限的约 85.25%；若只按 80% 可用空口预算则已经超限。因此工程必须实施码率约束、背压和丢弃策略，并在报告中说明实际源、编码参数和空口占用；不得保证未实测的画质或帧率。

## 3. 必须交付的完整工程

交付物必须是可从干净主机复现的 USRP 工程，而不是若干脚本或一次性实验命令。至少包含：

1. 清晰的目录结构及 `README`：支持的 OS、UHD/驱动版本、Python/C++ 运行时、依赖安装命令、构建命令、设备权限要求、已验证的 USRP 型号及未验证型号。
2. 可机器读取的配置清单（YAML/JSON/TOML 之一）：频率、4 MSPS、两 TX 通道、增益、带宽、时钟/时间源、RRC 参数、MRF/RVF2 版本、每流载荷长度、随机种子、队列上限和测试时长。CLI 覆盖配置时必须回显最终生效值。
3. 明确 CLI：`--dry-run`、设备发现/通道映射检查、向量发送、连续任意载荷发送、RVF2/视频发送、统计导出和安全发射开关。默认必须不发射；只有显式 `--enable-tx` 才可打开 TX。
4. 协议层：比特/字节序、header、两级 CRC、QPSK 映射、导频、训练、RRC、40-sample tail、双流同帧组合，全部直接使用或逐项比对本分支的规范与确定性向量。不得只以“接收端能看到能量”代替协议一致性。
5. 生产流水线：源帧/字节 -> 编码或 RVF2 分片 -> MRF 双流组帧 -> 矢量化比特/符号/IQ 生成 -> 有界 IQ 队列 -> 连续 UHD TX 写入。每个阶段必须有独立序号、时间戳或计数器，以及有界队列与背压策略。
6. 运行日志与结构化统计（JSON/CSV）：启动配置、每阶段吞吐、队列高水位、丢弃原因、UHD late/underflow/async error、短写、超时、已发样点、RF 帧序号、每流包数，以及停止原因。
7. 自动化测试：协议单元测试、确定性向量测试、无设备 dry-run、可选有设备但不打开 RF 的设备枚举/通道自检、可重复的连续发送压力测试命令。

## 4. 流水线与性能强制要求

### 4.1 必须做到

- 编码、组帧、波形生成和写无线电必须流水并发，生产/发送以块为单位推进；允许有限数量的预填充块，但不得把整段视频先全部调制到内存后才发送。
- IQ 队列必须是有界的。拥塞时必须记录并按明确策略背压、限码率或丢弃**完整且可识别的源帧/访问单元**；不得静默无限累积内存。
- 数字处理必须按数组/块矢量化。禁止每个符号、每个采样点调用系统调用或 UHD `send()`；禁止每符号启动/等待一次 DMA 或线程。
- 双通道必须作为同一 MRF 时间线按时启动（timed start）；必须记录所用 time source/clock source 和两通道映射。不能因顺序调用而允许两路帧边界漂移。
- UHD 短写时只重试**尚未写入的样点尾部**，并记录短写次数/样点数。不得从帧头或源文件头重复重发整帧。
- 每个访问单元（AU）与每个源视频帧必须只读取和编码一次；已成功排入/送出的 IQ 块不得因轮询或统计而重新读取、重新编码或整体重发。
- 连续模式结束、异常或 SIGINT 时必须停止产生新数据、排空或明确丢弃剩余有界队列、关闭 stream，并输出最终统计。不得留下隐式循环发射。

- 若在编码后丢弃预测AU，必须处理参考链：继续跳过依赖缺失参考的P帧，直到新的独立IDR，记录恢复事件；不得随机丢一个P帧后仍把后续解码失败视为RF故障。若在编码前降低源帧率，最终仍须满足至少30个新源帧/s，不能隐瞒丢弃。
- 所有“非流水线”禁令针对可重叠阶段的串行等待和逐符号I/O，不禁止算法内部真实依赖。单个发送API调用内部可以串行完成，但源读取、编码、组帧、IQ生产与设备供数必须有明确并行边界与有界缓冲。

### 4.2 明确禁止

- 禁止循环回放一个 IQ 缓冲区、一个 AU 或一个视频帧，并把显示刷新或“已发帧数”当作新视频帧率。循环模式只可作为标注为 `test-waveform-repeat` 的射频测试，不得用于视频性能验收。
- 禁止逐符号/逐 RF 帧等待接收端确认后再发下一帧；可靠性由 CRC、统计、上层限速/丢弃策略处理，重传机制若以后引入必须另行定义协议版本。
- 禁止静默降低 1024x600 分辨率、重复源帧、跳过帧身份统计，或把编码器输出帧率、显示器刷新率、USRP 写样点速率混作“视频帧率”。
- 禁止以“USRP 调用成功”“已发送样点数”或“频谱有能量”宣称 ZedBoard 收到有效 MRF 帧，更不得宣称已显示新视频。

## 5. 时钟、CFO 与双通道要求

当前 ZedBoard 接收机的窄 CFO 捕获无歧义范围约为 `±1e6/(2*32) = ±15.625 kHz`；独立 USRP 与板端本振/采样时钟绝不能假设零偏。首次联调的运行前提是：测量或受控配置后的初始频偏绝对值小于 10 kHz，并在日志中记录频率计划、设备参考源、中心频率、采样率和估计/测得 CFO。

若实际频偏超过该范围，USRP 工程不得把“已经发出”解释成接收机支持宽 CFO。宽 CFO 捕获、粗频偏搜索或更强的时钟同步是接收端后续独立功能，必须以新 feature、向量和回归测试交付后才可宣称支持。

双流使用的两条 TX 链必须是同一设备内可相干通道，或有明确的共享 10 MHz/PPS/时钟方案；工程必须检测并报告实际时钟与时间源。无法确认相干性时，只能运行单流诊断，不得报告 2x2 MIMO 通过。

## 6. 安全与物理链路前置条件

- 默认安全状态是 dry-run/不发射。真正 TX 需要 `--enable-tx`，并强制在日志中记录频点、每通道增益、带宽、线缆/衰减器说明和操作者确认。
- 有线 TX->RX 回环必须先配置外部衰减并核对端口连接；本工程不得自动把 TX 增益推至最大或依据猜测调整射频硬件。建议将“外接至少 30 dB 衰减器已接入”作为本项目受控回环测试的人工 checklist 项，而不是软件可替代的保证。
- 设备发现、时钟锁定状态、天线端口、通道号和发射许可必须在发射前打印。任何项目专用频率规划、法规/场地许可和最大安全功率均须由操作者确认。

## 7. 分阶段验收与必交证据

### A. 离线协议一致性（无 RF 硬件）

必须提交自动化测试日志，证明确定性输入在每个边界一致：payload 字节、header、两级 CRC、比特序、QPSK 符号、导频/训练位置、950 符号布局、RRC 后 3840 复样点。IQ 比对可以使用规范定义的定点/浮点容差或哈希；容差、版本和平台必须写出。此阶段只能证明发送波形生成正确，不能证明空口或接收机。

### B. USRP 连续发送工程就绪

必须提交：设备识别与版本、通道映射、有效配置回显、timed start 日志、至少一次规定时长的连续发送统计、IQ 队列高水位、短写/underflow/late/async 错误计数及退出日志。若没有对端接收机，本阶段报告必须明确为“仅本机/设备侧发送验证”。

### C. USRP 到 ZedBoard 的最小功能闭环

先用每流 128 B 的伪随机、递增和边界字节模式，不使用视频掩盖问题。ZedBoard 侧必须按空口规范输出可审计记录：RF 帧序号、两流 header/CRC/payload CRC 结果、期望与恢复 payload 的逐字节比对、丢失/错序/重复/CRC 失败计数、持续时长和实际 CFO。全部错误必须报告，禁止只摘取成功包。只有两流独立 payload 正确恢复后才进入 RVF2。

### D. RVF2 与视频性能闭环

要宣称 `1024x600 >= 30` 个真实新视频帧/s，必须同时提供：

- 输入源分辨率、像素格式、编码器与码率/关键帧配置；每个源帧带 session ID 与单调 frame ID。
- 发送、空口、接收、解码、显示各阶段的帧 ID 账本，能够证明显示的 30 fps 是 30 个不同 source frame，而不是重复显示、循环播放、低分辨率替代或仅 UI 刷新。
- 统计窗口、实际持续时间、frame ID 连续性、源帧产生率/丢弃率、RF 有效帧率、CRC 成功率、RVF2 重组成功率、显示新帧率、端到端 p50/p95 延迟。
- 实际比特率、每秒 RF 帧数、空口占用、两个流有效 fragment 数据率、所有队列高水位、UHD 所有异步错误及丢弃原因。

60 fps 是更高目标，必须以同一套“不同源帧”证据重新验收，不能从 30 fps 外推。若以可用空口预算 80% 作为工程裕量，则 RVF2 可用有效数据率约为 1.333 Mb/s；高于此预算的编码输出必须降码率、改协议/PHY 或明确报告不可达，不能悄悄积压。

## 8. 启动时的互操作配置契约

USRP 发射程序、板端接收服务和测试报告必须保存并比对以下字段：协议/向量版本、中心频率、RF 采样率、符号率、sps、RRC beta/taps、两 TX 通道映射、时钟与时间源、帧/包长度、CRC 多项式与初值、训练/导频序列与种子、payload 模式、RVF2 版本、编码参数、队列上限、启动时间和统计窗口。任一 PHY 字段不匹配时程序必须拒绝启动或以醒目错误退出，禁止“尽力发送”。

所有结果必须区分并分别报告：

1. USRP 提交/写入的 IQ 样点数；
2. 空口上由 ZedBoard 恢复且 CRC 有效的 MRF 帧/包数；
3. RVF2 成功重组的访问单元数；
4. 实际显示或消费的不同源视频帧数。

这四项不是同一个指标，任意一项都不能替代另一项。

## 9. 目前不允许声称完成的事项

### 性能设计与后续扩展门槛

本版4 MSPS是与现有接收机互操作的冻结基线，不是USRP或AD9361的硬件性能上限。完整工程必须测量源读取、编码、组帧/成形、UHD供数、接收检测和重组各阶段的持续吞吐及阻塞时间，注明CPU占用、队列驻留时间和空口有效利用率，定位最慢阶段后再扩展。不得以设备标称采样率推定端到端吞吐。

如果满足目标画质的1024x600/30 fps编码流无法装入本版有效容量及裕量，必须明确报告当前profile不满足要求，并提出收发两端一起升级的采样率/帧效率/调制编码方案、资源预算与回归验收；不能单方面改变USRP采样率或空口格式，也不能用低画质、重复帧或积压延迟冒充达标。画质验收需保存可比较的原始源与解码结果，报告编码设置、PSNR/SSIM或商定指标及可见失真，不能只报压缩码率。

RF联调阶段不依赖HDMI：先以接收端CRC、完整AU和解码后的不同源帧身份/图像质量验收；HDMI显示路径在RF/USRP联调成功后接入，不得让屏幕刷新阻塞无线收发。最终显示验收仍须独立证明新视频帧率。

在未完成 C 阶段前，不得声称 USRP 与 ZedBoard RF 协议联通；在未完成 D 阶段前，不得声称实现 1024x600/30 fps 或 60 fps 视频。当前板端 MHGD 在某些混合信道设置仍需独立验证，因此 USRP 工程的离线或本机发送成功也不等于端到端 MIMO 检测成功。任何未实测硬件数据、射频距离、商品性能或吞吐率均必须明确标为计划或理论值。
